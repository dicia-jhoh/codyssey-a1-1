## 이 미션의 위치 — 앞 미션에서 무엇을 이어받았나

이 프로그램의 기본 데이터는 **직접 지어낸 예시가 아니라 앞 미션에서 실제로 쓴 프롬프트**입니다.
미션 요구가 "이전 미션에서 작성한 프롬프트를 최소 3개 이상 기본 데이터로 등록"이기 때문입니다.

| 출처 미션 | 이어받은 프롬프트 | 어디에 들어갔나 |
|---|---|---|
| **B1-1** (LLM 업무 자동화) | 회의록 4구획 요약 시스템 프롬프트 · 업무 과업 입력 템플릿 | `data/seed_prompts.json` — 카테고리 "텍스트 생성" |
| **B1-2** (멀티모달 콘텐츠) | 제품 히어로샷 T2V 프롬프트 · 엔드카드 이미지 프롬프트 · 스타일 레퍼런스 추출 프롬프트 | 카테고리 "영상 생성" · "이미지 생성" |
| **B1-3** (노코드 자동화) | 워크플로우 분기 판정 프롬프트 | 카테고리 "자동화" |
| **B2-3** (소셜 콘텐츠) | 플랫폼별 변환 프롬프트 | 카테고리 "자동화" |

총 **7개**(요구 3개 이상). 각 항목에 `source` 필드로 출처 미션을 적어 두어, 프로그램 안에서도
"이 프롬프트가 어디서 왔는지" 보입니다(상세 보기 화면에 표시).

**코드에 문자열로 박지 않고 파일에서 읽는 이유**: 앞 미션 산출물이 원본이고 이 프로그램은 그것을
가져다 쓰는 쪽이라는 관계를, 주석이 아니라 **코드 구조로** 드러내기 위해서입니다
(`storage.load_seed()` 가 `data/seed_prompts.json` 을 읽습니다).

## 프로그램 구조 — 왜 파일을 4개로 나눴나

```
main.py       메뉴를 보여주고 고른 번호에 맞는 함수를 부른다 (시작 지점)
features.py   기능 12종 — 추가·검색·즐겨찾기·수정·삭제·내보내기…
ui.py         화면에 글자를 그리는 일만 한다 (데이터를 바꾸지 않는다)
storage.py    데이터를 만들고·읽고·저장한다 (화면 글자를 만들지 않는다)
data/seed_prompts.json   앞 미션에서 가져온 기본 프롬프트 7개
docs/run-log.md          전 기능 실행 결과 로그(실측)
```

**한 파일에 다 넣지 않은 이유**는 고칠 때 드러납니다. 목록 출력 모양을 바꾸고 싶으면 `ui.py` 만
열면 되고, 저장 형식을 바꾸고 싶으면 `storage.py` 만 열면 됩니다. 한 파일에 몰아넣으면
"출력을 고쳤는데 저장이 깨지는" 사고가 납니다.

**메뉴 번호 → 함수 연결도 표(dict)로 뒀습니다**:

```python
actions = {1: features.add_prompt, 2: features.show_all, ...}
```

`if/elif` 를 12번 쓰지 않고 표 한 줄로 대응시켰기 때문에, 기능을 늘릴 때 **표에 한 줄만 추가**하면 됩니다.

### 자료구조 — 왜 리스트 안에 딕셔너리인가

미션 제약이 "리스트와 딕셔너리를 사용"이라 그 안에서 골랐습니다. 판단 근거:

| 후보 | 장점 | 왜 안 골랐나 |
|---|---|---|
| **리스트 안에 딕셔너리** ✅ | 순서가 있어 "3번 프롬프트"로 고를 수 있고, 항목마다 이름 있는 필드(제목·카테고리…)를 가진다 | — |
| 딕셔너리 안에 딕셔너리(제목이 키) | 제목으로 바로 찾기 빠름 | **제목이 겹치면 앞의 것이 사라진다.** 순서도 번호로 못 고른다 |
| 리스트 안에 리스트 | 가장 단순 | `p[2]` 가 무엇인지 코드만 봐선 모른다. 필드가 늘면 전부 깨진다 |

프롬프트 1개는 항상 `storage.make_prompt()` 를 거쳐 만듭니다 — 만드는 곳을 한 군데로 묶으면
필드를 빠뜨린 항목이 생기지 않습니다.

### 기능별 동작 명세 — 입력이 잘못되면 무엇이 나오나

각 기능이 **정상일 때**와 **비어 있거나 잘못됐을 때** 어떻게 동작하는지입니다. 프로그램은 어떤 경우에도
꺼지지 않고 안내 메시지를 낸 뒤 메뉴로 돌아옵니다.

| 기능 | 정상 동작 | 예외 상황과 처리 |
|---|---|---|
| **1 추가** | 제목·내용·카테고리를 받아 목록 끝에 추가, `추가했습니다. (현재 N개)` | **제목을 비우고 엔터** → `제목은 비워 둘 수 없습니다.` 후 취소<br>**내용을 비우고 엔터** → `내용은 비워 둘 수 없습니다.` 후 취소<br>**카테고리에 없는 번호** → `잘못된 번호라서 '기타'로 지정했습니다.` (추가는 진행) |
| **2 전체 목록** | 번호 · ★/☆ · [카테고리] · 제목 · 내용 미리보기(28자) | **목록이 비었을 때** → `등록된 프롬프트가 없습니다.` (빈 화면만 나오면 고장으로 오해하므로 문구를 냅니다) |
| **3 카테고리별 조회** | 고른 카테고리의 항목만 출력 | **없는 카테고리 번호** → `없는 카테고리 번호입니다.`<br>**그 카테고리에 항목이 0개** → `'페르소나' 카테고리에는 등록된 프롬프트가 없습니다.` |
| **4 검색** | 제목·내용에 키워드가 든 항목을 **목록 형태로** 출력(`[검색 · T2V] 총 2개` 처럼 제목에 검색어 표시) | **검색어를 비우고 엔터** → `검색어를 입력하세요.`<br>**결과 0건** → `'xyz' 가 들어간 프롬프트가 없습니다.` |
| **5 상세 보기** | 내용 전문 + 출처 미션 + 조회수 출력, 조회수 +1 | **숫자가 아닌 입력** → `숫자를 입력하세요.`<br>**범위 밖 번호** → `1 ~ 7 사이의 번호를 입력하세요.` |
| **6 즐겨찾기 관리** | 고른 번호의 즐겨찾기를 켜고 끔 (`추가했습니다` / `해제했습니다`) | 5번과 동일한 번호 검사 |
| **7 즐겨찾기만 보기** | 즐겨찾기한 항목만 카테고리로 묶어 출력 | **하나도 없을 때** → `즐겨찾기한 프롬프트가 없습니다. 메뉴 6번에서 추가하세요.` (다음에 뭘 할지까지 알려줍니다) |
| **8 수정** | 제목·내용 변경. **엔터만 치면 기존 값 유지** | 번호 검사 동일 |
| **9 삭제** | `y` 를 입력해야 삭제 | **`y` 가 아닌 입력** → `취소했습니다.` (되돌릴 수 없는 동작이라 기본값이 취소입니다) |
| **10 조회수 Top** | 조회수 많은 순 정렬 출력 | **목록이 비었을 때** → `등록된 프롬프트가 없습니다.` |
| **11 저장/불러오기** | 1=저장, 2=불러오기 | **1·2 외 입력** → `1 또는 2를 입력하세요.`<br>**저장 파일이 없는데 불러오기** → `저장된 파일이 없습니다. 먼저 1번으로 저장하세요.` |
| **12 Markdown 내보내기** | 카테고리마다 파일 1개 생성 | **목록이 비었을 때** → `내보낼 프롬프트가 없습니다.`<br>**항목이 0개인 카테고리** → 그 파일은 만들지 않습니다(빈 파일을 남기지 않음) |

**프롬프트가 가진 정보(필드)**와 기본값:

| 필드 | 뜻 | 기본값 |
|---|---|---|
| `title` | 제목 | 필수 입력(빈 값 거부) |
| `content` | 내용(프롬프트 본문) | 필수 입력(빈 값 거부) |
| `category` | 6종 중 하나 | 잘못 고르면 `"기타"` |
| `favorite` | 즐겨찾기 여부 | **`False`(꺼짐)** — 새로 추가한 프롬프트는 항상 즐겨찾기가 아닌 상태로 시작합니다 |
| `source` | 출처 미션 | 새로 추가하면 `"직접 작성"`, 시드는 `"B1-1"` 등 |
| `views` | 조회수 | `0` |

**카테고리 선택 방식**: 자유 입력이 아니라 **6개 목록에서 번호로 고릅니다.** 자유 입력을 받으면
"이미지생성"·"이미지 생성"·"image" 가 전부 다른 카테고리가 되어 카테고리별 조회가 무의미해지기 때문입니다.
목록에 없는 분류가 필요하면 `storage.CATEGORIES` 에 한 줄을 추가하면 모든 기능(추가·조회·내보내기)에
자동으로 반영됩니다 — 분류 목록이 한 곳에만 있어서 가능한 일입니다.

### 종료 조건과 잘못된 입력 처리

- **종료 조건**: `while True` 안에서 `0` 을 입력했을 때만 `break`. 다른 어떤 입력으로도 루프가 끝나지 않습니다.
- **숫자가 아닌 입력**: `raw.isdigit()` 으로 먼저 걸러 `-1`(잘못된 값)로 바꿉니다. `int()` 를 바로 부르면 글자 입력에 프로그램이 죽습니다.
- **범위 밖 번호**: `actions.get(choice)` 가 `None` 이면 안내 후 `continue` — 메뉴로 돌아갑니다.
- **목록에서 번호 고르기**는 5개 기능이 똑같이 필요해 `_pick_index()` 하나로 묶었습니다(같은 검사 코드를 다섯 번 쓰지 않습니다).

## Git 사용 기록

### Git 이 무엇이고 왜 필요한가

**Git = 파일의 변경 이력을 시점마다 저장해 두는 도구**입니다. "최종.py / 최종_진짜.py / 최종_진짜최종.py"
로 폴더가 늘어나는 문제를 없애줍니다.

없으면 무슨 일이 생기나 — 이 프로젝트에서 실제로 겪을 상황으로 설명하면:

| 상황 | Git 이 없으면 | Git 이 있으면 |
|---|---|---|
| 즐겨찾기 출력을 고치다 망가뜨림 | 어디를 바꿨는지 기억에 의존, 되돌리기 어려움 | `git checkout` 으로 직전 커밋 상태로 즉시 복구 |
| 새 기능을 실험하고 싶음 | 원본을 복사해 두거나 그냥 덮어씀 | **브랜치**를 따로 만들어 본선(main)을 건드리지 않고 실험 |
| "언제 왜 이렇게 바꿨더라?" | 알 수 없음 | `git log` 에 변경 의도가 커밋 메시지로 남음 |
| 다른 컴퓨터에서 이어서 작업 | USB·메일로 파일 전달 | `push`/`clone` 으로 어디서든 같은 이력을 받음 |
| 여러 명이 같은 파일 수정 | 한 사람 작업이 덮여 사라짐 | `merge` 가 변경을 합치고, 충돌은 표시해 줌 |

핵심 개념은 셋입니다 — **커밋**(변경을 시점으로 저장), **브랜치**(작업 갈래를 나눔),
**원격 저장소**(GitHub 에 올려 백업·공유). 이 저장소의 이력이 그 셋을 전부 보여줍니다.

### 각 명령이 무엇을 하나

| 명령 | 하는 일 | 이 프로젝트에서 |
|---|---|---|
| `init` | 폴더를 Git 저장소로 만든다(빈 이력 시작) | [`docs/git-init-practice.md`](docs/git-init-practice.md) 에 실습 기록 |
| `add` | 변경 파일을 커밋 대상 목록(스테이지)에 올린다 | 매 커밋 전 `git add` |
| `commit` | 스테이지에 올린 변경을 이력에 저장한다 | 11회 — 기능 단위 |
| `push` | 로컬 이력을 GitHub(원격)에 올린다 | 저작 완료 후 |
| `pull` | 원격 변경을 로컬로 받아온다 | `git pull --rebase origin main` |
| `checkout` | 브랜치·시점을 이동한다 | `feature/favorites` 분기·복귀 |
| `clone` | 원격 저장소를 통째로 내려받는다 | `octocat/Hello-World` 실습 |
| `merge` | 갈라진 브랜치를 합친다 | `feature/favorites` → `main` |

**`add` 와 `commit` 이 나뉜 이유**: 고친 파일 전부가 아니라 **한 가지 의도에 해당하는 파일만 골라**
커밋하기 위해서입니다. 이 저장소에서 `ui.py` 와 `storage.py` 를 따로 커밋할 수 있었던 것도 그래서입니다.

### 커밋 이력 (10개 이상, 기능 단위)

`git log --oneline --graph --decorate --all` 실행 결과 원문:


`*` 하나가 커밋 하나, `|\` 부분이 브랜치가 갈라졌다 병합된 자리입니다.
작성자 정보가 실제로 커밋에 박혔는지도 확인했습니다:

```
$ git log --format='%h %an <%ae> %ad %s' --date=short | head -3

```

**커밋을 나눈 기준**: "한 커밋 = 한 가지 변경 의도". 그래서 데이터 계층·화면 계층·기능 계층이
각각 따로 커밋돼 있습니다. 나중에 문제가 생겼을 때 어느 커밋으로 돌아갈지 고를 수 있어야 하는데,
전부 한 커밋이면 되돌리기가 전부 아니면 전무가 됩니다.

### 브랜치 생성 및 병합

```bash
git checkout -b feature/favorites   # 즐겨찾기 개선용 브랜치 분기
# ... 커밋 2개 ...
git checkout main
git merge --no-ff feature/favorites  # 병합 기록을 남기며 합치기
```

`--no-ff` 를 쓴 이유: 그냥 `merge` 하면 커밋이 일렬로 붙어 **"여기서 갈라졌다 합쳐졌다"는 기록이 사라집니다.**
`--no-ff` 는 병합 커밋을 따로 만들어 그래프에 갈래를 남깁니다(위 이력의 `|\` 부분).

## 심층 인터뷰 대응 — 코드의 어디에서 어떻게 동작하나

### Q1. 입력 검증(범위·빈 값) 로직을 코드의 어느 부분에 두었고 어떻게 동작하나?

검증은 **세 층**으로 나뉘어 있고, 각 층이 서로 다른 종류의 잘못된 입력을 막습니다.

| 층 | 위치 | 무엇을 막나 | 어떻게 |
|---|---|---|---|
| ① 메뉴 번호 | `main.py` → `choose_menu()` | 숫자가 아닌 입력 | `raw.isdigit()` 이 거짓이면 `-1` 반환 → `actions.get(-1)` 이 `None` → 안내 후 `continue` |
| ② 목록 번호 | `features.py` → `_pick_index()` | 숫자 아님 · 범위 밖 · 빈 목록 | 세 검사를 순서대로: 빈 목록이면 즉시 `None`, `isdigit()` 검사, `0 <= index < len(prompts)` 범위 검사 |
| ③ 필드 값 | `features.add_prompt()` | 제목·내용 빈 문자열 | `input(...).strip()` 후 `if not title:` — 공백만 친 경우도 `strip()` 이 빈 문자열로 만들어 함께 걸립니다 |

**`int()` 를 바로 부르지 않는 이유**: `int("abc")` 는 `ValueError` 로 프로그램을 종료시킵니다.
`isdigit()` 으로 먼저 걸러 예외 자체가 발생하지 않게 했습니다(`try/except` 로 잡는 방법도 있지만,
"애초에 잘못된 값을 통과시키지 않는" 쪽이 흐름을 읽기 쉽습니다).

**검증을 `_pick_index()` 한 곳에 모은 이유**: 상세 보기·즐겨찾기·수정·삭제 4개 기능이 똑같이
"목록에서 번호 고르기"를 합니다. 각자 검사하면 한 곳만 고쳐 놓고 나머지를 빠뜨리는 일이 생깁니다.

```python
index = int(raw) - 1          # 화면은 1번부터, 리스트는 0번부터 → 항상 1을 뺀다
if index < 0 or index >= len(prompts):
    ui.notice(f"1 ~ {len(prompts)} 사이의 번호를 입력하세요.")
    return None
```

### Q2. 커밋을 기능 단위로 나눈 구체적 기준은?

"한 커밋 = 한 가지 변경 의도"를 실제로 판정한 규칙은 넷입니다.

1. **되돌릴 단위인가** — 이 변경만 취소하고 싶어질 수 있으면 따로 커밋합니다. `ui.py` 미리보기 추가와
   즐겨찾기 묶음 출력을 나눈 이유가 이것입니다(미리보기가 마음에 안 들면 그 커밋만 되돌립니다).
2. **계층이 다른가** — 데이터(`storage.py`) · 화면(`ui.py`) · 기능(`features.py`) 은 관심사가 달라
   항상 따로 커밋했습니다.
3. **커밋 메시지를 "그리고" 없이 쓸 수 있는가** — "A 하고 B 했다"가 되면 두 커밋으로 쪼갭니다.
4. **동작하는 상태인가** — 각 커밋 시점에서 `python main.py` 가 실행돼야 합니다. 중간에 깨진 커밋이
   있으면 그 지점으로 되돌릴 수 없어 이력의 가치가 떨어집니다.

접두어(`feat`·`docs`·`chore`)는 변경 종류를, 괄호(`feat(ui)`)는 영향 범위를 나타냅니다 —
`git log --oneline` 만 훑어도 무엇이 바뀌었는지 보입니다.

### Q3. 리스트와 딕셔너리를 왜 그렇게 조합했나 (동작 원리)

- **리스트**는 값을 **순서대로 늘어놓은** 자료구조입니다. 자리마다 번호(인덱스)가 있어
  `prompts[2]` 로 즉시 꺼냅니다. 순서가 있다는 성질이 "3번 프롬프트를 고르세요"를 가능하게 합니다.
- **딕셔너리**는 **이름표(키)로 값을 찾는** 자료구조입니다. 내부적으로 키를 해시(숫자 지문)로 바꿔
  저장 위치를 계산하므로, 항목이 몇 개든 `prompt["title"]` 을 찾는 속도가 거의 일정합니다.
  대신 **같은 키를 두 번 넣으면 나중 값이 앞의 값을 덮어씁니다.**

그래서 조합이 정해집니다 — **바깥은 리스트**(프롬프트에 순서·번호가 필요하니까),
**안쪽은 딕셔너리**(항목마다 제목·카테고리·즐겨찾기처럼 **이름 있는 여러 값**을 담아야 하니까).

바깥을 딕셔너리(제목이 키)로 하면 안 되는 이유가 위의 "덮어쓴다" 성질입니다 — 제목이 같은
프롬프트를 두 개 만들면 **앞의 것이 조용히 사라집니다.** 사용자가 지운 적 없는 데이터가 없어지는 건
가장 나쁜 종류의 버그라, 순서와 중복을 허용하는 리스트를 바깥에 뒀습니다.

### Q4. 메뉴 반복에 `while` 을 쓴 이유와 종료 조건 설계

**`for` 가 아니라 `while` 인 이유**: `for` 는 **반복 횟수가 정해진** 경우에 씁니다(목록 7개를 훑는 등).
메뉴는 사용자가 몇 번 조작할지 프로그램이 알 수 없습니다 — 3번 만에 끝낼 수도, 50번 쓸 수도 있습니다.
**끝나는 시점이 조건에 달린 반복**이 `while` 입니다.

```python
while True:          # 조건을 True 로 두고
    ...
    if choice == 0:  # 안에서 명시적으로만 빠져나온다
        break
```

`while True` + `break` 로 쓴 이유는 **탈출 지점이 하나뿐임을 코드에 드러내기** 위해서입니다.
`while choice != 0:` 로 쓰면 첫 반복 전에 `choice` 를 미리 정해 둬야 하고(초기값 문제),
"어디서 끝나는가"가 조건식과 본문에 나뉘어 흩어집니다.

**종료 조건이 `0` 인 이유**: 기능 번호는 1부터 매기고 `0` 을 종료로 예약했습니다.
기능이 12개에서 20개로 늘어도 종료 번호는 그대로 `0` 입니다 — "마지막 번호가 종료"로 하면
기능을 추가할 때마다 종료 번호가 바뀌어 사용자가 헷갈립니다.

**`continue` 의 역할**: 잘못된 번호일 때 `continue` 로 루프 처음으로 돌아가 메뉴를 다시 그립니다.
`continue` 가 없으면 `action(prompts)` 가 `None` 을 호출하려다 프로그램이 죽습니다.

### Q5. 검색은 어떻게 구현했나

```python
low = keyword.lower()
found = [p for p in prompts
         if low in p["title"].lower() or low in p["content"].lower()]
```

세 부분으로 나뉩니다:

1. **`in` 연산자** — 문자열 안에 다른 문자열이 들어 있는지 검사합니다(부분 일치).
   `"T2V" in "제품 히어로샷 T2V 프롬프트"` → `True`. 완전 일치가 아니라 부분 일치를 쓴 이유는
   사용자가 제목 전체를 기억하지 못하기 때문입니다.
2. **`.lower()` 양쪽에 적용** — 검색어와 대상 **둘 다** 소문자로 바꿔 비교합니다. 한쪽만 바꾸면
   `"t2v"` 로 검색했을 때 `"T2V"` 를 못 찾습니다.
3. **리스트 컴프리헨션** — `[p for p in prompts if 조건]` 은 "조건에 맞는 것만 모아 새 리스트를
   만든다"는 뜻입니다. 원본 `prompts` 는 건드리지 않고 **새 목록**을 만들기 때문에, 검색 결과를
   보여주는 것만으로 데이터가 바뀌는 사고가 없습니다.

**제목과 내용을 `or` 로 묶은 이유**: 프롬프트는 제목보다 본문에 특징적인 단어가 있는 경우가 많습니다
(예: `"dolly-in"` 은 제목엔 없고 내용에만 있음). 둘 중 하나만 맞아도 결과에 넣습니다.

결과는 `ui.show_list(found, title=f"검색 · {keyword}")` 로 **전체 목록과 똑같은 형식**으로 출력합니다 —
사용자가 새 화면 읽는 법을 다시 배우지 않아도 됩니다. 결과가 0건이면 목록 대신 안내 문구를 냅니다.

### Q6. 브랜치를 왜 분리했고 병합 시점·기준은 무엇인가

**분리한 이유**: `feature/favorites` 작업은 **이미 동작하는 기능(즐겨찾기 출력)을 손보는 일**이었습니다.
손보다가 망가뜨리면 `main` 이 깨집니다. 브랜치를 따로 두면 `main` 은 언제나 동작하는 상태로 남고,
실험은 격리된 곳에서 합니다. 실패하면 브랜치를 그냥 지우면 됩니다.

**브랜치를 나눌 기준**(이 프로젝트 규칙):
- 여러 커밋에 걸치는 작업이면 브랜치 → 한 커밋으로 끝나면 `main` 에서 바로.
- 결과가 마음에 안 들어 통째로 버릴 가능성이 있으면 브랜치.
- 이름은 `feature/<대상>` — 무엇을 건드리는 갈래인지 이름만 봐도 알게.

**병합 시점 기준**(세 개를 모두 만족할 때만 `merge`):
1. 브랜치에서 **의도한 변경이 끝났고**,
2. `python main.py` 로 **직접 실행해 동작을 확인했고**(즐겨찾기 목록이 카테고리로 묶여 나오는지),
3. 커밋 메시지가 정리돼 이력이 읽히는 상태.

**`--no-ff` 를 쓴 이유**: 기본 `merge` 는 브랜치 커밋을 `main` 에 일렬로 붙여
**"여기서 갈라졌다 합쳐졌다"는 사실이 사라집니다.** `--no-ff` 는 병합 커밋을 따로 만들어
그래프에 갈래를 남기므로, 나중에 "즐겨찾기 개선 작업 전체"를 한 덩어리로 되돌릴 수 있습니다.

**충돌(conflict)이 났다면**: 이번엔 브랜치와 `main` 이 서로 다른 파일을 고쳐 충돌이 없었습니다.
같은 줄을 양쪽에서 고쳤다면 Git 이 파일에 `<<<<<<<` / `=======` / `>>>>>>>` 표시를 넣습니다.
해결 순서는 ① 표시된 부분을 열어 **양쪽 의도를 확인**하고 ② 최종 코드를 직접 고른 뒤
③ 표시를 지우고 ④ `git add` 로 "해결했다"고 알린 다음 ⑤ `git commit` 으로 병합을 마칩니다.
자동 해결에 맡기지 않는 이유는, 어느 쪽이 맞는지는 **의도를 아는 사람만** 판단할 수 있기 때문입니다.

### Q7. 영속화(저장) 설계 — 무엇을 남기고 무엇을 버리나

미션 요구가 "실행 중에 추가한 것은 유지, **종료하면 초기화**"라 기본 동작은 **메모리에만** 둡니다
(`prompts` 리스트 하나가 프로그램이 켜져 있는 동안의 전부).

보너스 기능으로 저장을 붙이면서 규칙을 셋 정했습니다:

| 규칙 | 내용 | 왜 |
|---|---|---|
| **시드와 사용자 데이터를 분리** | 시드 = `data/seed_prompts.json`(커밋), 사용자 = `data/prompts_user.json`(gitignore) | 시드는 모두에게 같아야 하고, 사용자 데이터는 사람마다 다릅니다. 한 파일에 섞으면 저장소를 받을 때마다 남의 데이터가 딸려옵니다 |
| **저장은 명시적으로만** | 메뉴 11번을 눌러야 저장 | 자동 저장이면 "종료 시 초기화"라는 미션 요구가 깨집니다 |
| **불러오기는 통째로 교체** | `prompts.clear()` 후 `extend()` | 아래 설명 |

**`prompts = loaded` 가 아니라 `clear()` + `extend()` 를 쓴 이유**(중요):
`prompts = loaded` 는 **이 함수 안의 이름만** 새 리스트를 가리키게 바꿉니다. `main.py` 가 들고 있는
원래 리스트는 그대로라, 불러오기를 해도 화면에는 예전 목록이 나옵니다. `clear()` + `extend()` 는
**같은 리스트 객체의 내용을 바꾸므로** 그 리스트를 보고 있는 모든 곳에 반영됩니다.

**JSON 을 고른 이유**: 표준 라이브러리 `json` 만으로 읽고 쓸 수 있고(외부 라이브러리 금지 제약 충족),
사람이 파일을 열어 눈으로 읽을 수 있으며, 딕셔너리 구조가 그대로 보존됩니다.
`ensure_ascii=False` 를 준 것은 한글이 `제목` 같은 코드로 저장되지 않게 하기 위해서입니다.

### Q8. 같은 제목의 프롬프트가 들어오면 — 중복·충돌 처리 규칙

**허용합니다.** 같은 제목이어도 내용이 다를 수 있고(예: "요약 프롬프트 v1"·"v2"), 리스트는 순서로
구분하므로 덮어쓰기가 일어나지 않습니다. 사용자가 만든 데이터를 프로그램이 임의로 거부하거나
합치지 않는다는 원칙입니다.

- **식별은 제목이 아니라 목록 번호(위치)로** 합니다 — 수정·삭제·상세 보기 전부 번호로 고릅니다.
- **불러오기는 병합이 아니라 교체**입니다. 병합하면 "같은 항목인가"를 판정해야 하는데,
  그 판정 기준(제목? 내용? 둘 다?)이 틀리면 데이터가 소리 없이 사라지거나 두 배로 늘어납니다.
  교체는 결과가 명확합니다 — 파일에 있던 것이 전부, 그 외는 없음.
- **자동 중복 제거를 넣지 않은 이유**: "비슷한 프롬프트"는 사용자가 일부러 만드는 경우가 많아,
  프로그램이 지우면 의도한 작업을 되돌리는 셈이 됩니다.

### Q9. 카테고리를 늘리려면 어디를 고치나 (확장성)

`storage.py` 의 `CATEGORIES` 목록 **한 줄만** 추가하면 됩니다.

```python
CATEGORIES = ["텍스트 생성", "이미지 생성", "영상 생성", "페르소나", "자동화", "기타",
              "코드 생성"]   # ← 추가
```

이 한 줄이 세 곳에 자동 반영됩니다 — 추가 화면의 선택지(`ui.show_categories`), 카테고리별 조회의
번호 매핑(`features.show_by_category`), Markdown 내보내기의 파일 목록(`features.export_markdown`).
**분류 이름이 여러 파일에 흩어져 있었다면 하나만 고치고 나머지를 빠뜨려**, 추가 화면에는 있는데
조회에는 안 나오는 상태가 됩니다. "같은 사실은 한 곳에만 적는다"는 원칙을 지킨 결과입니다.

## 용어 사전

| 용어 | 뜻 (이 문서에서) |
|---|---|
| **터미널(명령 프롬프트)** | 글자로 명령을 입력하는 검은 창. Windows=명령 프롬프트/PowerShell, Mac=터미널 |
| **저장소(repository, repo)** | 프로젝트 폴더 하나를 Git 이 관리하는 단위 |
| **커밋(commit)** | 변경 내용을 "여기까지 완료"로 저장하는 것. 사진 한 장을 찍어 두는 것과 비슷 |
| **브랜치(branch)** | 작업 갈래. 본선(main)을 건드리지 않고 따로 실험할 때 만든다 |
| **병합(merge)** | 갈라진 브랜치를 다시 합치는 것 |
| **push / pull** | 내 컴퓨터 → GitHub 올리기 / GitHub → 내 컴퓨터 받아오기 |
| **clone** | GitHub 저장소를 내 컴퓨터로 통째로 내려받는 것 |
| **`.gitignore`** | Git 이 관리하지 않을 파일 목록. 캐시·개인 데이터를 넣는다 |
| **딕셔너리(dict)** | `{"제목": "값"}` 처럼 이름표로 값을 꺼내는 자료구조 |
| **리스트(list)** | `[1, 2, 3]` 처럼 순서대로 담는 자료구조 |
| **함수(function)** | 이름 붙인 작업 덩어리. `def 이름():` 으로 만든다 |
| **시드 데이터(seed)** | 프로그램을 처음 켰을 때 이미 들어 있는 기본 자료 |

   안 나오면 python.org 에서 설치하고 "Add Python to PATH" 를 반드시 체크하세요.
2. **Git 설치·설정 확인** — `git --version` 으로 설치를 확인하고, 이름·이메일을 등록합니다.
   ```bash
   git config --global user.name "내이름"
   git config --global user.email "내메일@example.com"
   git config --global init.defaultBranch main
   ```
   이걸 안 하면 커밋에 작성자가 안 남습니다.
3. **저장소 내려받기** — `git clone https://github.com/dicia-jhoh/codyssey-a1-1.git`
4. **폴더로 이동** — `cd codyssey-a1-1`
5. **실행** — `python main.py`. 프롬프트 7개를 불러왔다는 메시지가 뜨면 성공입니다.
6. **둘러보기** — `2`(전체 목록) → `5`(상세 보기) → 번호 → 내용 전문이 나오는지 확인합니다.

9. **종료** — `0`. 저장하지 않은 추가분은 사라집니다(설계상 그렇습니다).
10. **직접 고쳐 보기** — 카테고리를 늘리고 싶으면 `storage.py` 의 `CATEGORIES` 목록에 한 줄을 추가하고 다시 실행하세요.
